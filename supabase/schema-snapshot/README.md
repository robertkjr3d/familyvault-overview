# schema-snapshot

`schema.sql` = the live database's structure as SQL text, generated by `dump-schema.sql` (read-only, contains **no user data**).

**Status: `schema.sql` has NOT been generated yet (as of 2026-09-28).** Steps to create/refresh it:

1. Supabase dashboard -> SQL Editor -> paste all of `dump-schema.sql` -> Run.
2. Export the result as CSV (results panel "Export"/"Download CSV").
3. Give the CSV to Claude (or any AI) with the request "turn this into supabase/schema-snapshot/schema.sql". The assembly is mechanical: sort rows by the first column, write the second column, prefix with:
   ```
   -- REFERENCE ONLY: do not run against the live database.
   SET check_function_bodies = false;
   SET search_path = public, extensions;
   ```
4. Commit `schema.sql`. Refresh after any batch of SQL changes, and about monthly.

`dump-schema.sql` was tested (2026-09-28) on a local PostgreSQL mock of the Supabase layout: replaying its output into an empty database and dumping again gave an identical result. It has not been run against the real project until step 1 above is done.

Sections in the output (sort key prefix): 010 extensions, 020 enums, 030 tables, 040 constraints, 050 indexes, 060 functions, 061 function EXECUTE grants, 070 views, 080 RLS enabled, 081 **tables with RLS disabled**, 090 policies (public + storage), 100 triggers (incl. `auth.users`), 110 table grants, 120 storage buckets.

Not captured: table data, `auth.users` rows, storage files, Edge/Worker code (in this repo), scheduled jobs inside Supabase (pg_cron, if any), secrets.
